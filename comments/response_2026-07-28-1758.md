## R1 (high) — the fixed quadrature misses ordinary cells near strong correlation

**Confirmed, and the mechanism is exactly as described.** Reproducing the
review's observation through the retained TMB objective:

```text
rho = 0.999900   margin intervals [0, 0.855470476] x [0.525045584, 0.565191835]
adaptive-quad cell probability = 0.040146250934120269
package NLL = 57.030296876230   reference NLL = 3.215226219434   loss = 53.815 nats
```

I then measured the geometry that causes it, which makes the failure
arithmetic rather than mysterious. The integrand is a smoothed indicator of
`[q(b')/rho, q(b)/rho]` whose edges have width `s/|rho|`:

```text
plateau [qbm/rho, qb/rho] = [0.0628, 0.1642] width 0.1013, sigma = 0.0141
interval [-7.941, 1.060] width 9.00; 20-pt node spacing ~0.450
```

A plateau of width 0.10 inside an interval of width 9.00, sampled at a
spacing of 0.45. The rule steps over it. Nothing about non-negativity helps.

### What I changed

`gaussian_cell_prob()` now clips the interval to the window where the
integrand is not negligible, then splits it at `±GAUSS_EDGE` around each edge
centre, giving five panels each smooth on its own scale, with 16 nodes per
panel. Cut points are clamped into the retained interval and then forced
non-decreasing by a running maximum, so a panel can collapse to nothing (when
the plateau is narrower than the brackets, or the window clips an edge away)
without ever acquiring a negative width, and the union of panels is exactly
the retained interval however many collapse.

The panel constants are measured, not chosen by eye. Sweeping a 3,600-cell
grid against `stats::integrate()` across `rho` from 0 to ±0.99999:

| configuration | worst relative error |
|---|---|
| 1 panel, 20 nodes (shipped in `4a1ba7b`) | 7.6e-01 |
| 5 panels, window 6 | 1.0e+00 |
| 5 panels, window 10, bracket 3, 12 nodes | 2.3e-05 |
| **5 panels, window 10, bracket 4, 16 nodes** | **7.0e-07** |

The `window 6` row is the reason I tested the window rather than assuming it:
too tight a window truncates real mass and is *worse* than no window at all.
I would have shipped that if I had only tested the configuration I expected
to use.

On the review's own observation the fixed template now returns
`3.215226219434` against a reference of `3.215226219434` — the loss is zero to
twelve digits.

Cost is 80 nodes against 20. I recovered half of that by moving the
saturated-tail branch from the two `pnorm` *results* to their *arguments*:
`CppAD::CondExp` evaluates both value branches, so the previous form put four
`pnorm` calls on the tape per node where two suffice. Net cost is ~2x for a
six-order-of-magnitude accuracy gain in the worst case.

**Regression added.** `tests/testthat/test-fit-copula.R`, "Gaussian stays
accurate at strong correlation", checks `z_dep` in `{2, 3, 4, 5}`
(`rho` up to 0.9999) against `stats::integrate()`. The margins are built
comonotonically so cells stay on the diagonal and keep comfortably
representable probabilities, and the test asserts `min(p) > 1e-8` first — the
review's point that a reference near the rounding floor proves nothing is the
same reason the pre-existing moderate-dependence test stops at `z_dep = 1`,
and it needed a different data design rather than a wider loop.

## R2 (high) — the `1e15` cap destroys the strong-dependence likelihood

**Confirmed.** My reproduction of the symmetric cell `y1 = y2 = 1` at
`mu = 1`, `m = 0.5`:

```text
z_dep=  2.0 theta=      7.389  exact=0.19780177102975377  package=0.19780177102975344
z_dep=  5.0 theta=      148.4  exact=0.29077392633165633  package=0.15036147107747305
z_dep= 20.0 theta=  4.852e+08  exact=(cancels to 0)       package=2.4276858031166409e-10
comonotonic limit P(Y = 1) = 0.29629629629629628
```

The algebra was right — 15-digit agreement at `z_dep = 2` — and the cap alone
broke it.

**My reasoning in the comment was wrong, not merely imprecise.** I wrote that
beyond `1e15`, `(1 + x)^k` is indistinguishable from `x^k`. That statement is
true and irrelevant. The cap does not drop the `+1`; it replaces `x` itself,
and the result then raises the ratio to the power `k = -1/theta`. Capping
therefore discards `|k| * (log x - 34.5)` in the exponent, which is `O(1)`
whenever `theta` is large. I checked the negligibility of the wrong term.

### What I changed

`clayton_cell_prob()` now carries `x` and `y` as **logarithms** end to end and
never forms them. Every quantity the result needs is a function of
`log1p(x)`, `log1p(y)` and `log(1 + x + y)`, each reachable from `log x` and
`log y` by log-sum-exp. `theta` reaches 4.85e8, so `a^-theta` overflows a
double for any `a` bounded away from 1 while `log x` is an ordinary number
near 1e8. The cap is deleted, not raised.

Supporting this required `nb2_cdf_pair()` to return its log-space
accumulators, which it already computes internally and was discarding.

### Correction: my first attempt at this fix was wrong twice

This section originally claimed the fix was complete, on the strength of the
strong-dependence numbers below. It was not. The truck refit died at its first
inner Newton step, and running it down found two further defects **that I had
introduced in this response's own R2 rewrite**. Both are fixed; I am recording
them because the first draft of this document asserted a correctness I had not
established.

**A — I discarded the marginal mass.** The rewrite computed `log(u/u')` as
`log_a - log_am`. Once the NB2 CDF saturates those two are equal to the last
bit, so the difference is exactly zero, `log()` of it is `-Inf`, and every
derivative through it is NaN. On the truck margins at `mu = 1` that is all 197
counts from `y = 70` up, covering 50 of the 3,487 observations, and the
difference is already 32% wrong at `y = 69` before it collapses. This is the
same cancellation `clayton_cell_prob()` was written to remove — I reintroduced
it in log space. The ratio is now built from the marginal mass, which
`nb2_cdf_pair()` carries to full relative precision (1.45e-125 at `y = 266`,
where the CDF difference gives 0). The tell was in my own diff: I threaded
`log_pmf` out of the recursion and then never used it.

**B — a factor-of-3.7 error in every tail cell.** This section originally
argued that

```text
1 - xy/((1+x)(1+y)) = (1 + x + y) / ((1+x)(1+y))
```

lets `log1p(-w)` be computed as `log(1+x+y) - log1p(x) - log1p(y)`. That
identity is exact and the computation is safe only for LARGE `x, y`. For small
`x, y` all three logs are `O(x+y)` while their difference is `O(xy)`, so it
underflows to exactly zero. Expanding the bracket shows why that matters:

```text
(1+x+y)^k - (1+x)^k - (1+y)^k + 1 = k(k-1)xy + O(3)
```

and the two terms of the return are `-k*xy` and `k^2*xy` — the SAME order.
Zeroing the first returns `C00*k^2*xy` instead of `C00*k(k-1)*xy`, a factor of
`k/(k-1)`: 3.7 at `theta = e`, and worse as `theta` falls. The original code
used `log1p(-xy/((1+x)(1+y)))`, which is accurate for small `x, y` and fails
for large; my replacement was accurate for large and failed for small. Neither
form works at both ends, so the code now branches on `log w`, building `log w`
additively (no cancellation) and using the three-log difference only where
`x, y` are large enough for the logs to be well separated.

B is the sharper lesson of this review cycle. It produced a cell probability
that was positive, smooth, finite, differentiable — and wrong by a factor of
3.7. That is precisely the failure the review's R1 identified, committed a
second time, in the paragraph where I explained why it could not happen.

After the fix, including A and B:

```text
z_dep=  5.0  exact=0.29077392633165633  package=0.290773926331656
z_dep= 10.0  package=0.29625900048809001
z_dep= 20.0  package=0.29629629460304252   (comonotonic 0.29629629629629628)
```

and, on three independent references rather than one:

| check | result |
|---|---|
| deep tail (`y` to 266) vs the Taylor asymptotic `C00*k(k-1)*x*y` | agrees to ~1e-13 in `log p` |
| well-conditioned cells vs the exact four-corner formula | relative error 0 to 2e-14 |
| comonotonic limit | 0.29629629460 against 0.29629629630 |

The asymptotic is deliberately not a re-implementation of the formula under
test. A whole-formula R reference written with `x` and `y` in linear space
goes negative from `y = 40` on, and one written in log space merely restates
the implementation. The asymptotic is a different expression reached a
different way, and it is what caught B.

Beyond `z_dep ≈ 7` the four-corner reference cancels to exactly zero in double
precision, so the package is now returning the right answer in a region where
the naive reference cannot follow it — which is the whole point of the
rewrite, and the reason the review was right to use the comonotonic limit as
the check there rather than a four-corner value.

**Regressions added.** "Clayton reaches its comonotonic limit at strong
dependence" checks exact four-corner agreement at `z_dep` in `{1, 2, 5}`,
convergence to `P(Y = 1)` at `z_dep = 20`, and that the approach is monotone
from below across `z_dep` in `{5, 8, 11, 14, 17, 20}`.

"Clayton stays finite and accurate where the CDF saturates" covers A and B.
For A it asserts the GRADIENT and HESSIAN are finite at truck-like counts, not
just the value — the `-Inf` left the objective finite and poisoned only the
derivatives, which is exactly why the pre-existing value-only tail test passed
while the Laplace fit died at its first inner Newton step. For B it compares
`log p` against the asymptotic at `y` in `{69, 100, 180, 266}`, and guards
that the reference really is in the saturated tail so the check cannot pass
vacuously.

## R3 (high) — the taped objective depended on the starting values

**Confirmed.** Two tapes for the same observation, evaluated at an identical
parameter vector:

```text
F(0) at the extreme tape point = 0 (underflows: TRUE)
default-tape NLL = 2.256476515341
extreme-tape NLL = 1.591500211747
```

This one is unambiguous: an objective value at a fixed parameter vector must
not depend on where its tape was built.

The review also caught that my own comment claimed the branches were
"selected on the observed counts alone" while the code tested
`asDouble(am) == 0.0`. The comment described the fix I intended; the code did
something else. `asDouble()` resolves at tape construction, and `am` is a
parameter-dependent CDF that underflows to exactly zero for positive counts in
ordinary regions — `P(Y <= 0)` at `mu = r = 2000` is `0.5^2000`.

### What I changed

The branches are now selected from `Y1_int(i) == 0` / `Y2_int(i) == 0`, passed
in as `bool` arguments. `Y1_int`/`Y2_int` are cast from `DATA_VECTOR` at the
top of the objective and are already used for the NB2 loop bounds, so they
carry no parameter dependence onto the tape. The Poisson-margin path sets the
same flags and guards its `log()` calls with them.

After the fix both tapes return `2.256476515341`, difference exactly 0.

**Regression added.** "Clayton's taped objective does not depend on the
starting values" builds one tape at an underflowing custom start
(`mu = size = 2000`, asserted to underflow) and one at the default, then
requires both to agree at the same target vector.

## A note on what this cycle exposed

Two of the three high findings trace to one habit: I verified the property I
had set out to establish and stopped. For Clayton I proved the algebra exact
in a well-conditioned regime and never tested where the cap activates. For
Gaussian I proved the strip integral non-negative and convergent at moderate
`rho` and never tested where the conditional transition narrows. Both tests I
wrote would pass on the broken code, because both were written to confirm the
fix rather than to find its edges.

Defect B above is the same habit surviving the lesson. Having just written
that non-negativity is not accuracy, I replaced one conditionally-safe
expression with another, verified it in the regime I had been thinking about,
and shipped a cell probability wrong by a factor of 3.7 everywhere else — in
the same commit, explaining why that could not happen. What caught it was not
care but a reference constructed to be independent of the thing it checked,
and an end-to-end run on real data.

Two practices earned their keep and are worth stating as the actual takeaway:
every reference gets a guard asserting it is trustworthy in the regime where
it is used (that guard is what flagged my own bad reference here), and a
numerical claim is not established until something that does not share the
implementation's algebra agrees with it.
